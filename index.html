If Rust waits for the network, that thread waits too.

Speaking notes

Kotlin reaches Rust through JNA. Swift calls the native C function directly. In either app, the call stays on the thread that made it. Both generated bindings turn text into UTF-8 bytes in a RustBuffer; Rust takes ownership as a String. The result follows the return path. If Rust waits for the network, that thread waits too. Calling from a worker keeps this wait off the UI thread.

For discussion

The buffer also says how much memory was allocated for it. A string passed on its own uses the buffer’s length. If a string sits inside a record, its encoded data includes a separate length. The same-thread drawing follows one call; the Rust function can still start other work on other threads.

During a synchronous call, ordinary call-local state uses that thread’s stack or registers. A Rust String owns a separate allocation for its UTF-8 bytes. Heap objects can outlive a call when another object keeps ownership of them; a synchronous return does not empty the Rust heap. The compiler can optimize the exact placement of local values.

Async Rust call

Rust compiles this function into a state machine. Calling it creates a future.

Simplified example adapted from the Rust async export 

#[uniffi::export]
pub async fn greet_async(who: String) -> String {
    black_box().await; // The next slide fills in this part.

    format!("Hello, {who}!")
}

A future has no thread or runtime of its own.
UniFFI’s generated Kotlin or Swift code calls poll to make progress.

Sources: Rust async semantics   Future::poll

Speaking notes

Rust turns this async function into a state machine at compile time. Calling the function creates a future that stores its arguments. It does nothing until someone calls poll. Poll runs the next part and saves what is needed if the function has to wait. The future has no thread or runtime of its own. UniFFI’s generated Kotlin or Swift code makes the poll calls. A library used by the future may still require Tokio.

For discussion

An await may finish immediately. Writing async does not guarantee a pause, work on another thread, or a heap allocation. UniFFI does put its future on the heap. A library used by that future may still require Tokio or another service to watch for events and run the future again.

The displayed greet_async function is an illustrative adaptation of UniFFI’s say_after export: the timer is replaced with black_box().await, and the delay argument is removed. black_box is a placeholder for an async operation, not std::hint::black_box or a complete implementation. The next slide fills it with a call to an async trait implementation supplied by Kotlin or Swift. The original timer explicitly starts a sleeping Rust thread; it does not start Tokio. It has been left out so that its implementation does not distract from how polling works.

“Static state machine” means the compiler generates a concrete future type and the code for moving between its states. It does not mean a static variable, an immutable value, or a value that must live forever. Its state changes at runtime. Calling an async function creates an instance of that type. poll advances it, but cannot call itself: a caller or executor must invoke it. A hand-written type can implement Future too. The Rust language does not require heap allocation for every future; UniFFI chooses it for this FFI lifetime.

Where does the Rust Future live

A foreign async task owns the future through a handle. UniFFI keeps it on the Rust heap.

Waiting keeps a lightweight task and a Rust future alive.
It does not reserve an OS thread.

Sources: Native state   Kotlin continuation map   Handle map   Rust String storage

Speaking notes

The Kotlin coroutine or Swift Task owns the Rust future through the handle held by its generated helper. The foreign runtime schedules that task to call poll across the FFI. Poll uses the executing thread’s stack. Once it returns and the task suspends, the same thread can process other tasks. We trade a thread blocked for the whole wait for a cheaper suspended task and the saved Rust future. UniFFI keeps the future and its captured values on the Rust heap, inside the same app process.

For discussion

This drawing covers both apps. Kotlin and Swift each keep a continuation that remembers how to resume their waiting code. In Kotlin, the dispatcher chooses where the coroutine runs, while its Job controls cancellation. The handle for a Rust future and the ID for a Kotlin continuation refer to different objects. UniFFI’s type requirements ensure that a future can be polled safely as execution moves between threads.

Task ownership and allocation

The foreign task owns the handle through the generated async helper. UniFFI stores the boxed future behind that handle. The helper releases it on exit using Kotlin finally or Swift defer. This ownership does not guarantee immediate cancellation: the inspected Swift helper keeps waiting after Task cancellation, as the later cancellation slide explains. A long or blocking poll still occupies its executing thread.

Which owner releases what?

OS: supplies the process address space and schedules its threads. Threads: each has its own stack. Crossing the C boundary uses the existing thread; it does not create another stack just for Rust. Rust/UniFFI: owns the allocations for the future and Rust values. Kotlin/Swift: owns its task or coroutine state and the handle used by the helper.

UniFFI allocates and pins the future on the heap

Self {
    future: Some(Box::pin(wrapped_future)),
    result: None,
}

The future’s stored String contains a pointer, length, and capacity; its UTF-8 bytes are in a separate allocation. An awaited operation can also own or share other state. UniFFI’s free drops its inner future and stored result. Any separately shared objects live until their remaining owners release them. A runtime or native library can create and manage threads, but the future itself owns no thread. A Waker requests another poll; it is not a saved Rust call stack.

Speaking notes

Think of the future as the operation’s saved state. Calling greet_async gives us a value that owns the name. UniFFI puts that value on the heap and keeps it at a stable address. Polling temporarily uses a thread’s stack. If the awaited operation is still waiting, poll returns and those Rust call frames are gone. The name and the awaited future remain in the state machine, so another poll can continue, even on another thread. Kotlin or Swift also remembers where its own code will resume. Those are separate pieces of state in the same process. Neither side needs to keep a thread blocked just to preserve its local values.

What is actually stored?

The compiler generates the concrete future type for the illustrative greet_async function. Its captured arguments and the values needed across the await belong to that state machine. Their exact field layout is a compiler detail. UniFFI wraps that future and stores it with Box::pin. Pinning keeps the future’s allocation at a stable address while it is being polled; moving the handle or polling from another thread does not move that allocation.

The who parameter is a Rust String. It owns a buffer of UTF-8 bytes through a pointer, length, and capacity. That buffer is separate from the allocation holding the future. This distinction is about ownership, not separate address spaces for each language.

The Rust handle and the foreign continuation are different things

The future handle represents an owned reference to UniFFI’s RustFuture object. That object contains the boxed future and its stored result. The handle implementation turns an Arc pointer into an opaque handle. Kotlin or Swift passes it back to generated FFI functions; application code does not dereference it.

The generated Kotlin and Swift helpers separately register a continuation so a Rust callback can resume their suspended code. The continuation remembers where the foreign-language computation resumes. A Rust Waker requests another poll. Neither mechanism saves a live Rust call stack. When a poll returns, the thread and its stack still exist, but that invocation’s Rust frames have returned.

Finishing changes what UniFFI owns

When polling finishes, UniFFI drops the boxed future and stores its lowered result for the bindings to collect:

UniFFI replaces the completed future with its result

Poll::Ready(result) => {
    self.future = None;
    self.result = Some(result);
    true
}

The generated bindings collect and convert the result, then release the handle. The Kotlin helper does this cleanup in finally; Swift uses defer. Their cancellation behavior differs, as the next slide explains. Shared objects can outlive the future if another owner retains them. A foreign async operation also has Kotlin or Swift state. Its result and drop callbacks connect that state to the Rust future; their ownership must be coordinated during completion and cancellation.

Async gives us a place to stop between polls. Kotlin’s helper uses that: cancelling its Job can free the Rust future. What cancellation stops

Observation: Kotlin’s generated helper waits with suspendCancellableCoroutine and calls freeFunc in finally. Cancelling its Job while suspended schedules the coroutine to leave the wait with a cancellation exception. Cleanup does not need another Rust wakeup. See Kotlin’s cancellation contract.

Rust cleanup drops the stored future and result

fn free(&mut self) {
    self.future = None;
    self.result = None;
}

Consequence: dropping the future stops its remaining async body and runs destructors for values it owns. It does not undo completed side effects or automatically stop independent work. Any independently spawned task, thread, or non-cancellable I/O needs its own lifetime and stop mechanism.

Limit: poll runs Rust inline, and free needs the same mutex. If a poll blocks for five minutes, cancelling the caller cannot shorten those five minutes. Adding async or await does not guarantee a pause; the future being awaited has to return Pending. Rust’s Future contract says poll should return quickly. A busy caller dispatcher or a slow destructor can also delay cleanup.

Sync can cooperate too: a synchronous operation can check a cancellation flag or expose an interrupt handle that another thread calls. Application-services already has SqlInterruptHandle. Cancelling a Kotlin Job or Swift Task alone does not add this mechanism to an ordinary synchronous FFI call.

Swift differs: the inspected outbound helper uses withUnsafeContinuation without a task cancellation handler. Cancelling that Swift Task alone does not end its wait and drop the Rust future. The next slide shows the two helpers side by side.

An Activity stopping, an Activity being destroyed, a ViewModel being cleared, and the process ending are different events. The app decides which event should end a particular operation.

Closing a screen, cancellation, suspension, and process death

Closing a screen: an Activity or view can disappear while the app process stays alive. That does not by itself unload the Rust library. The app’s chosen Job, task, and component lifetimes decide which work is cancelled.

OS suspension: while a process is suspended, its threads do not execute, including Rust threads. A stored future stays in memory until the app resumes or the OS discards the process. iOS restricts background execution; Android also limits or freezes cached processes. The presence of a future grants no background execution permission.

Graceful cleanup: while the process still runs, normal cancellation and explicit shutdown can drop the Rust future and release resources. That behavior is different from a forced process kill. Kotlin’s helper is cancellable; the inspected Swift helper does not stop waiting merely because its Task was cancelled.

Process termination: the OS stops every thread in this process, including any Rust-created worker threads, and reclaims its memory. Android does not guarantee onDestroy on process death, and iOS does not guarantee a final app termination callback. No Rust destructor or coroutine cleanup can be assumed to run after a forced kill. Rust’s explicit process::exit also skips stack destructors.

After restart: handles, pointers, call stacks, and futures from the old process are gone. Data already saved to storage, a request already received by a server, or work delegated to an OS service may outlive that process; the original in-process Rust future does not.
